## 2026-11-14 週間負荷の見せ方
- 内容：部位別は横棒（単色）、推移は部位ごとの小さな棒グラフ（スモールマルチプル）。週は月曜始まり
- 理由：8部位を色分けした積み上げ棒は色の区別が難しく読みにくい。部位名をラベルにして単色にすれば色覚に関係なく読める。推移は全部位で同じ目盛りにして部位どうしを比べられるようにした
- 補足：ボリュームは自重種目（0kg）を含まないため、セット数を既定の指標にした

## 2026-11-14 ファイル取得は毎回サーバーに確認し、起動失敗時は自動復旧する
- 理由：ビルドなし構成のため、ファイル名にバージョンが付かず、キャッシュで新旧ファイルが混ざると起動しない
- 却下案：import にバージョン番号を付ける（更新のたびに手で書き換える必要があり、書き忘れの危険）、ビルドツールの導入（構成が重くなる）

## 2026-11-14 「〇〇の日」の表示はしない
- 内容：部位の日のバッジ・事前に決める機能はやめ、筋肉の絵で記録した部位を示すだけにする
- 理由：ユーザーの判断。筋トレアプリらしい見た目を優先
- 見直し条件：ユーザーから再度要望があったとき（実装は打ち消しコミット 33ef097 の対象 da49a6e に残っている）

## 2026-11-14 公開方法は GitHub Pages（リポジトリを公開）
- 内容：GitHub Actions で main の `app/` を公開。テストが失敗したら公開しない
- 理由：設定が最も手軽。コードに秘密情報はなく、記録データは各iPhone内にあるため公開されない
- 却下案：Cloudflare Pages（非公開のまま使えるが、アカウント登録と連携の手間がかかる）
- 注意：今後も秘密情報（APIキー等）をコミットしないこと。Firebase を追加する場合、Firebaseの公開用設定値はコードに含めてよいが、セキュリティルールで保護すること

## 2026-11-14 外部から提案された多機能仕様（React構成・ルーティン・分析等）は見送る
- 内容：休憩タイマーのみ採用。技術構成は素のJavaScriptのまま
- 理由：「機能が多すぎないこと」が出発点。まずシンプルな版を実際に使ってから必要な機能を判断する
- 将来の候補：重量推移グラフ、種目のID管理（名前変更に強くする）、配色の変更、ルーティン

## 2026-11-14 筋トレ記録のデータは端末内保存＋CSVバックアップにする
- 内容：localStorage に保存し、共有メニューからCSVでGoogleドライブ等へバックアップ
- 理由：設定不要ですぐ使える。オフラインのジムでも動く。CSVはスプレッドシートで開ける
- 却下案：Googleスプレッドシート＋Apps Script（初回設定が煩雑）、Googleドライブ直接保存（OAuth設定が重く、ホーム画面アプリでログインが不安定）、Firebase（今は不要。将来の候補）
- 見直し条件：複数端末で使いたい、他の人にも使ってもらう、自動同期が欲しくなったとき → Firebase を検討
- 補足：ロジックは `lib.js` に分離してあり、保存先を差し替えやすい構造にしている

## 2026-11-14 フレームワーク・ビルドなしの素のJavaScriptにする
- 理由：機能が少なく、依存ライブラリなしで保守が楽。スマホ環境からも修正しやすい
- 見直し条件：画面や機能が大きく増えたとき

## 2026-11-14 Git運用：確認してから main に反映する
- 内容：作業ブランチでコミット → ユーザーに確認 → 承認後に main へプッシュ
- 理由：PRのマージ操作なしで手軽に運用しつつ、無断で main が変わらないようにするため
- 却下案：毎回PRを作成（スマホでの操作が増える）、無確認で main に直接プッシュ（意図しない変更のリスク）
- 見直し条件：複数人で開発する、または本番運用を始めるとき
