# コード品質・テスト・エラー処理

## 設計・品質
- DRY / KISS / 単一責任を意識しつつ、過剰な抽象化は避ける。
- ビジネスロジック、UI、DBアクセスを分離する。
- 説明的で一貫した命名。マジックナンバーを避ける。
- 既存の技術スタック、フォーマッター、命名規則に従う。
- 不要な依存ライブラリを追加しない。追加する場合は必要性・保守状況・脆弱性を確認する。
- コメントには「何をするか」より「なぜそうするか」を書く。
- 短さより読みやすさを優先する。

## 型・入力検証
- TypeScriptは strict を基本とし、any を避ける。Pythonは型ヒントを使う。
- 外部データは型・形式・桁数・範囲・必須項目を検証する。
- NULL、未定義、空文字、ゼロを混同しない。

## エラー処理・ログ
- 例外を握りつぶさない。エラーを無視して成功扱いにしない。
- 原因を追跡できるログを残す。ただし機密情報は出さない。
- 利用者にはわかりやすいメッセージを出し、スタックトレースや内部パスは見せない。
- 通信失敗、タイムアウトを考慮し、再試行による二重処理を防ぐ。

## テスト
- 新機能にはテストを、バグ修正には再発防止テストを追加する。
- 正常系・異常系・境界値を確認する。金額、税、在庫、日付、権限は重点的に。
- テストを削除・無効化して成功扱いにしない。失敗したら原因を調査する。
- 実行できなかったテストと残リスクを報告する。

## 既存機能の保護
- 変更前に関連コードと依存関係を調べ、変更範囲は最小限にする。
- 既存のAPI、ファイル形式、DBスキーマ、画面動作への影響を確認する。
- 問題解決のために既存機能を削除・無効化しない。
- 既存の「バグっぽい挙動」も業務上の依存がないか確認してから直す。
