# データベース設計・整合性・移行

## 設計
- 第3正規形を基本とし、マスタ・トランザクション・履歴を分離する。
- 主キー、外部キー、UNIQUE、NOT NULL、CHECK制約を使い、整合性をアプリ側だけに依存させない。
- 命名規則を統一する。
- 金額は浮動小数点を避け、整数単位または10進型で扱う。
- 識別コード（JAN、商品コード等）は文字列で保持し、先頭ゼロを失わない。
- 日時のタイムゾーン、NULLの意味を明確にする。
- 非正規化する場合は理由を示し、整合性維持の仕組みを設ける。

## トランザクション・整合性
- 一体で成功/失敗すべき更新はトランザクションで管理し、失敗時はロールバックする。
- 同時更新の競合を考慮する（楽観ロック・排他制御）。
- 再実行による二重登録を防ぐ。
- 丸め・端数処理・税計算のルールを明示する。
- 外部APIとDBにまたがる更新は部分失敗と再実行を考慮する。

## 変更・移行・バックアップ
- 構造変更はバージョン管理されたマイグレーションで行い、既存データを保持する方法を優先する。
- 破壊的変更、本番DBの削除・初期化・再構築は事前承認を得る。
- 重要な変更前にバックアップと復元手順を確認する。検証せずに復元可能と断定しない。
- 全削除・再投入を安易に採用しない。
- DB変更時は docs/INDEX.md やスキーマ資料を更新する。

## パフォーマンス
- N+1クエリや不要なDBアクセスを避け、必要に応じてインデックスを検討する。
- 大量データはページング・バッチ処理を検討する。
- 性能を理由に整合性を犠牲にしない。
